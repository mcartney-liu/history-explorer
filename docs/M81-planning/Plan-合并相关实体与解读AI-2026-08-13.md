# 方案：合并「相关实体」与「解读与 AI」两个区块

> 提出：PO（翔哥）2026-08-13
> 状态：**待 PO 审批，未动工**（按 FRW 铁律，审批前不写代码）
> 决策类型：前端交互架构（P3 层面）

---

## 一、现状问题

实体页「研究」tab 下有两个区块，**展示的实体高度重叠**：

| 区块 | 组件 | 标题 | 内容 | 数据来源 |
|------|------|------|------|---------|
| ① 相关实体 | `EntityRelatedList` | 「相关实体 · 可以继续追问」 | 实体名 + 类型 + 推荐理由（如"通过强关系 related_to 相连"） | `GET /api/v1/related-entities`（独立请求，最多 6 条） |
| ② 解读与 AI | `InterpretationPanel` + `AIExplanationPanel` | 「解读与 AI」 | 关系解读卡（实体 + 关系强度条 + 解释文案）+ AI 溯源问答 | `entity.connections_explained`（后端返回）+ relationships 本地推导 |

**用户感知**：同一批实体（罗马、凯撒、拜占庭…）在页面上出现两遍——一个是"还有哪些可研究"的列表，一个是"为什么值得探索"的解读卡。数量上：①最多 6 个，②解读卡若干 + AI 问答，两者集合高度重合。

## 二、合并目标

**合成一个区**：每个实体只出现一次，但**同时承载"是什么 + 为什么值得探索"**两个信息量，AI 问答保留为区内独立子块。

## 三、方案设计

### 3.1 结构（单一区）

```
┌─ 解读与 AI（合并后唯一标题）─────────────────────┐
│                                                 │
│  ▍ 关联实体 · 值得探索          （原①的实体集）   │
│  ┌─────────────────────────────────────────────┐ │
│  │ [罗马]        Location   相关度 ████ 1.00    │ │
│  │   为什么：通过强关系 related_to 直接相连…     │ │
│  │   ↓ 点击进入该实体                            │ │
│  └─────────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────────┐ │
│  │ [拜占庭帝国]   Civilization  相关度 ███ 0.90  │ │
│  │   为什么：通过 inherited 关系相连，时间相近…   │ │
│  └─────────────────────────────────────────────┘ │
│  …（最多 6 条，与现①数量一致）                    │
│                                                 │
│  ▍ 向 AI 追问              （原②的 AI 问答）     │
│  ┌─────────────────────────────────────────────┐ │
│  │ [输入框] 问 AI…                              │ │
│  └─────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

### 3.2 每个卡片的合并信息

| 字段 | 来源 |
|------|------|
| 实体名 + 类型徽标 | ①（related-entities 的 target_entity） |
| 相关度条（0~1 强度） | ②（connections_explained 的 score 可视化，`he-interpret-strength`） |
| 为什么值得探索（一句话） | ①的 reasons 首条 **或** ②的 explanation，取信息更全者 |
| 点击行为 | ①：点击进入该实体 → 保留（研究链路有逻辑可点） |

### 3.3 数据合并策略（关键决策）

两处数据源不同（①走 API、②随 entity 下发），合并方式二选一：

- **方案 X（推荐，改动小）**：以**①相关实体列表为主容器**，在其卡片内**增强展示**②的强度条与解释。EntityRelatedList 保持调 API，InterpretationPanel 保留但其"解读卡"部分由 EntityRelatedList 吸收，InterpretationPanel 只剩 AI 问答 + 历史意义。
- **方案 Y（改动大）**：后端把两路数据合并成单一响应，前端只调一次接口。更干净但动后端，违反"改动只增不改"成本更高。

> 推荐 X：纯前端，EntityRelatedList 增强 + InterpretationPanel 裁剪，风险小、可单步 revert。

### 3.4 保留/移除明细

| 元素 | 处理 |
|------|------|
| EntityRelatedList 的"实体列表" | **保留**，作为主容器 |
| EntityRelatedList 的 reason 文案 | 保留 |
| InterpretationPanel 的解读卡（he-interpret-grid） | **并入** EntityRelatedList 卡片（强度条 + explanation） |
| InterpretationPanel 的"历史意义"（understandings） | 保留（这是单独信息，不重复） |
| AIExplanationPanel（AI 问答） | 保留，放在合并区底部 |
| 原「相关实体 · 可以继续追问」标题 | 改为「关联实体 · 值得探索」或并入「解读与 AI」 |

## 四、涉及文件（预估）

| 文件 | 改动 |
|------|------|
| `frontend/src/components/EntityRelatedList.tsx` | 增强卡片：加强度条 + explanation 字段 |
| `frontend/src/components/InterpretationPanel.tsx` | 裁剪：移除解读卡部分（或改造 props） |
| `frontend/src/components/EntityPage.tsx` | 重组区块：EntityRelatedList 与 InterpretationPanel 合并为一个 section |
| `frontend/src/styles/*.css` | 卡片样式微调 |
| 相关测试（EntityRelatedList.test / EntityPage.test） | 适配新结构 |

**不改后端**、不改数据、不动 AI 网关。

## 五、验收标准

1. 「研究」tab 下**只出现一个区**（解读与 AI），相关实体不再单独出现
2. 每个实体卡片同时含：实体名、类型、强度条、"为什么值得探索"文案
3. 点击实体卡仍能进入该实体（研究链路不丢）
4. AI 问答、历史意义保留
5. 相关测试全绿，TS 零错误，Freeze 通过

## 六、风险与回退

- 纯前端改动，风险低；单步 revert 可完整回退
- 若合并不符合预期，可退回现状（两个区块）
