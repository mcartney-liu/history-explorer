## Executive Summary

## 1. 数据流全景（Committed Baseline）

### 1.1 两条独立的 Exploration 路径

```
路径 A: 实时 Explore (App.tsx)
═══════════════════════════════════
GET /explore/{topic}
  ↓ ExplorationResult (App.tsx:90-105)
  ↓ MainEntityCard / TimelinePanel / ConnectionsExplainedPanel...
  ↓ ❌ 不含 causal_statements 字段
  ↓ ❌ 不渲染 GuidePanel / PackageJourney

路径 B: Exploration Package (ExplorationPackagePage.tsx)
═══════════════════════════════════════════════════════════
getPackageBySlug(slug) → 静态 JSON
  ↓ CHINA_CAUSAL_STATEMENTS 硬编码常量 (L18-59)
  ↓ GuidePanel ← causalStatements prop (L146)
  ↓ PackageJourney → RelationshipChain ← causalStatements prop (L169)
  ↓ ✅ 渲染 CausalStatementCard
```

**关键发现**：CausalStatement 的消费完全发生在路径 B 中，而路径 B 不调用任何 API。ExploredNode 修复只影响路径 A。

### 1.2 后端 ExplorationResult 现状

```python
@dataclass
class ExplorationResult:  # M82 P1.4/P1.5 scope
    source: str
    target: Optional[str]
    paths: list[PathCandidate]     # ← PathCandidate 已有 causal_statements ✅
    explanation: str

    def to_dict(self) -> dict:
        return {
            "source": self.source,
            "target": self.target,
            "paths": [p.to_dict() for p in self.paths],  # ← causal_statements 已在序列化中 ✅
            "explanation": self.explanation,
        }
```

**`ExplorationResult` 已正确传递 `causal_statements`**（通过 `PathCandidate.to_dict()`）。问题仅在于 `ExploredNode`——它是 `explore()` API 的返回类型，而非 `find_connections` API 的返回类型。

### 1.3 两个后端 API 的区别

| API | 后端函数 | 返回类型 | causal_statements 状态 |
| --- | --- | --- | --- |
| `GET /explore/{gid}` | `explore()` | `list[ExploredNode]` | ❌ ExploredNode 缺少字段 |
| `find_connections(a, b)` | `find_connections()` | `ExplorationResult` | ✅ PathCandidate 已有 |

前端 `App.tsx` 调用的是 `GET /explore/{topic}`，对应 `explore()` → `ExploredNode`。`ExplorationResult` / `find_connections` 在前端未被直接消费。

## 6. 数据源替换方案

### 6.1 问题

`ExplorationPackagePage` 不调用 `/explore/{gid}` API——它使用静态 `getPackageBySlug(slug)` 获取包数据。硬编码 CS 删除后，数据必须从另一个来源获取。

### 6.2 可行方案

| 方案 | 描述 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **方案 X**：从 App.tsx 传递 causalStatements | App.tsx 在 `fetchNode()` 后提取 `causal_statements`，通过 props 传递给 ExplorationPackagePage | 与现有数据流一致（App.tsx 已有 `setResult`） | 需要确认 ExplorationPackagePage 是否在 App.tsx 的渲染树中；需要修改 App.tsx 渲染逻辑 |
| **方案 Y**：ExplorationPackagePage 内部 fetch | ExplorationPackagePage 内部调用 `/explore/{gid}` API，提取 causal_statements | 自包含，不依赖 App.tsx | 额外的 API 调用；增加页面加载瀑布流 |
| **方案 Z**：package JSON 嵌入 causal_statements | 将 CS 数据直接写入 `explorationPackages.ts` 的 package 定义中 | 最简单的实现 | 与方案 A 同样的问题（双重数据源），只是从硬编码常量移到 package JSON |

### 6.3 推荐：方案 X

```
App.tsx fetchNode()
  ↓
  setResult(data as ExplorationResult)  // 已有
  ↓
  提取 data.paths[].causal_statements  // 新增
  ↓
  传递给 ExplorationPackagePage via props  // 新增
```

**理由**：
1. 不引入额外的 API 调用
2. 利用已有的 `ExplorationResult` 数据流（`PathCandidate.causal_statements` 已正确序列化）
3. 变更范围最小

### 6.4 关键前提

**方案 X 的前提是 App.tsx 的渲染树中确实包含 ExplorationPackagePage**。如果 ExplorationPackagePage 是通过路由独立渲染的（而非 App.tsx 的子组件），则需要方案 Y。

这一前提需要在 Implementation 前通过代码审查确认。
