## §2 Semantic Relationship Model — 三方案评估

### 2.1 核心约束

任何 M85 方案必须满足：

```
C1: 不把 KG 边包装成 Semantic Edge
    KG Relationship ≠ Semantic Relationship
    如果两个 CausalObject 的 cause/effect 在 KG 中已有连接，
    Semantic Layer 不重复表达。

C2: 不引入 AI 自动发现关系
    Relationship 来源 = Curator authored
    不是 LLM 推理、不是图算法推导

C3: 三层关系可区分
    KG / Semantic / Navigation 必须能回溯分类

C4: 不建立 Semantic Graph
    related_causal_objects 是静态链接列表，不是图索引
    不做 BFS/DFS traversal
```

### 2.2 方案 A：简单引用（CausalObject 字段扩展）

```json
{
  "id": "co-004",
  "cause_id": "china_v1:idea-qinzhi",
  "effect_id": "china_v1:idea-sanxing-liubu",
  "mechanism": "...",
  "consequence": "...",
  "related_entities": [...],
  "exploration_paths": [...],
  
  // M85 新增
  "related_causal_objects": [
    {
      "target_id": "co-001",
      "relation_type": "institutional_evolution",
      "explanation": "秦制建立的中央集权框架，为科举制度的出现提供了制度前提"
    }
  ]
}
```

| 维度 | 评价 |
| --- | --- |
| **架构复杂度** | 🟢 最低 — 一个字段，CausalObject 11 字段（从 10 扩展） |
| **KG 边界** | 🟢 安全 — 单向引用，不写入 KG |
| **AI 风险** | 🟢 安全 — Curator 手动维护 |
| **Explorer 体验** | 🟡 中等 — Detail Page 底部展示"相关解释"列表 |
| **可演化性** | 🟡 中等 — 关系类型是 enum string，未来可能需要更丰富的表达 |
| **风险** | 关系扁平化，无法区分 "制度演化" vs "文明对比" vs "技术互补" 的差异 |

**判定**：最安全，最符合 M84.5 的"最小变更"原则。但关系表达能力有限。

### 2.3 方案 B：Semantic Relationship 作为独立 Object

```
CausalObject A          SemanticRelationship          CausalObject B
┌──────────────┐       ┌─────────────────────┐       ┌──────────────┐
│ co-004       │───→   │ sr-001              │   ←───│ co-001       │
│ 秦制→三省六部  │       │ type: evolution      │       │ 科举→文官     │
│              │       │ mechanism: "..."     │       │              │
│              │       │ confidence: medium   │       │              │
└──────────────┘       └─────────────────────┘       └──────────────┘
```

| 维度 | 评价 |
| --- | --- |
| **架构复杂度** | 🔴 高 — 新 Object 类型，新 Model，新 API，新 UI |
| **KG 边界** | 🟡 中等 — 独立的 Semantic Layer 实体，但增加了抽象层次 |
| **AI 风险** | 🟡 中等 — 独立 Object 更容易被 AI 管线盯上 |
| **Explorer 体验** | 🟢 好 — 关系有自己的 Detail Page，可独立探索 |
| **可演化性** | 🟢 好 — 关系类型可独立扩展 |
| **风险** | 过度设计。M84 的原则是 "只有一个实例时不抽象"。SemanticRelationship 目前只有 4 个候选（Curator #1/#4/#5/#7），不足以支撑独立 Object 类型 |

**判定**：方向正确但时机过早。M85 不应该为 4 个关系创建新的 Object 类型。等 M86+ 关系数量达到 20+ 且出现多种关系子类型时再考虑。

### 2.4 方案 C：Exploration Context 扩展（轻量路径标注）

```json
{
  "id": "co-004",
  "exploration_paths": [
    // M84 已有：KG 探索路径
    {
      "from": "china_v1:idea-sanxing-liubu",
      "to": "china_v1:idea-neige",
      "relationship": "evolved_into",
      "label": "三省六部如何催生内阁制度"
    },
    
    // M85 新增：Semantic 探索路径（指向另一个 CausalObject）
    {
      "from_object": "co-004",
      "to_object": "co-001",
      "path_type": "semantic",
      "relation": "institutional_evolution",
      "label": "秦制的中央集权如何为科举制度提供前提"
    }
  ]
}
```

| 维度 | 评价 |
| --- | --- |
| **架构复杂度** | 🟢 低 — 复用 exploration_paths 结构，不新增顶层字段 |
| **KG 边界** | 🟢 安全 — path_type="semantic" 明确标记非 KG 路径 |
| **AI 风险** | 🟢 安全 — Curator 手动维护 |
| **Explorer 体验** | 🟡 中等 — exploration_paths 中混入两种类型的路径 |
| **可演化性** | 🟡 中等 — 如果 Semantic 路径数量增长，exploration_paths 会变得臃肿 |
| **风险** | KG 路径和 Semantic 路径混在同一列表中，增加了 UI 层的区分成本 |

**判定**：比方案 A 更优雅（复用已有结构），但比方案 A 更容易混淆 KG 和 Semantic 路径。

### 2.5 推荐方案

```
方案 A — 简单引用（related_causal_objects 字段）
```

**理由**：

1. **最小变更**：1 个字段（CausalObject 10→11），0 新 Model，0 新 API 端点（复用现有 CausalObject API，前端从 JSON 中解析）
2. **最安全**：单向引用，不写入 KG，不建立 Semantic Graph
3. **M84.5 证据充分**：3/3 Explorer 的跨对象需求可以被一个静态引用列表覆盖——不需要更复杂的表达
4. **可回退**：如果 M85 验证失败，删除一个字段即可，不影响任何已有架构
5. **为方案 B 留空间**：如果 M86+ 关系数量达到 20+，可以从 `related_causal_objects` 升级为独立的 SemanticRelationship Object

## §3 Relationship Model — 最小定义

### 3.1 RelatedCausalObjectRef

```python
@dataclass(frozen=True)
class RelatedCausalObjectRef:
    """M85 — A curator-authored semantic link between two CausalObjects.
    
    This is NOT a KG edge. It does NOT write to the Knowledge Graph.
    It is a curator's judgment that understanding Object A helps
    understand Object B.
    """
    target_id: str                    # CausalObject ID
    relation_type: str                # "institutional_evolution" | "technological_chain" | "civilization_contrast" | "ideological_influence" | ...
    explanation: str                  # Curator-authored explanation of the relationship
```

### 3.2 CausalObject 扩展

```
CausalObject（M84，10 字段）
  ...
  + related_causal_objects: Tuple[RelatedCausalObjectRef, ...]  ← M85 新增

CausalObject（M85，11 字段）
```

### 3.3 关系类型（初始 enum）

| relation_type | 含义 | 示例 |
| --- | --- | --- |
| `institutional_evolution` | 制度演化关系 | co-004（秦制）→ co-001（科举） |
| `technological_chain` | 技术链关系 | co-008（印刷术）→ co-011（造纸术） |
| `civilization_contrast` | 文明对比关系 | co-009（罗马法）→ co-004（秦制） |
| `ideological_influence` | 思想影响关系 | co-013（佛教）→ co-014（理学） |

**约束**：relation_type 是 curator 判断，不是系统推导。初始 4 种，M86+ 可扩展。

### 3.4 禁止的关系类型

| 禁止 | 理由 |
| --- | --- |
| `kg_derived` | KG 边包装——违反 C1 |
| `ai_generated` | AI 生成——违反 C2 |
| `recommended` | 推荐引擎——属于 Navigation Layer，非 Semantic Layer |
| `similar_to` | 过于模糊——无法区分 Semantic vs Navigation |

## §4 KG Boundary — 三层关系分离

### 4.1 三层关系定义

```
KG Relationship（事实层）
  定义：两个 Entity 之间存在的事实连接
  示例：china_v1:idea-qinzhi → caused → china_v1:idea-sanxing-liubu
  来源：KG 数据
  表达：Graph Edge

Semantic Relationship（解释层）← M85 新增
  定义：Curator 认为理解 Object A 有助于理解 Object B
  示例：co-004（秦制→三省六部）→ co-001（科举→文官）
  来源：Curator 策展
  表达：related_causal_objects 字段

Navigation Relationship（交互层）
  定义：系统根据 Explorer 行为推荐的探索路径
  示例："你可能还想了解..."
  来源：Explorer 行为数据（M86+）
  表达：推荐引擎（M86+，不在 M85 范围内）
```

### 4.2 判定规则

```
如果一个关系对同时满足以下条件 → KG Relationship（不在 M85 范围）：

  A.cause_id 或 A.effect_id 与 B.cause_id 或 B.effect_id 在 KG 中存在
  直接的 Relationship（caused / influenced / evolved_into 等）

如果一个关系对满足以下条件 → Semantic Relationship（M85 范围）：

  A 和 B 的解释逻辑相关（Curator 判断），
  但 A 和 B 的 cause/effect Entity 在 KG 中无直接连接

如果一个关系对满足以下条件 → Navigation Relationship（M86+）：

  Curator 认为 Explorer 可能对对比/扩展感兴趣，
  但两个 CausalObject 的解释逻辑不构成理解链
```

### 4.3 P2 的修正——重要边界案例

```
co-008（印刷术→知识传播）和 co-011（造纸术→知识传播）

KG 视角：两个 CausalObject 的 effect 相同（知识传播）→ KG 关系
Explorer 视角：造纸术如何为印刷术提供前提？→ 理解链需求

M85 处理：
  如果 Curator 判断"理解造纸术有助于理解印刷术的革命性"→ Semantic
  如果只是"它们 effect 相同"→ 不纳入 related_causal_objects

这个案例说明：KG 连接 ≠ Semantic 连接，但 Explorer 可能需要二者都有。
M85 不因为 KG 已有关联就排除 Semantic 关系——关键是 Curator 判断是否存在额外的理解价值。
```

**修订 C1**：

```
C1（修订）：不把 KG 边包装成 Semantic Edge。
但如果 Explorer 对 KG 关联有额外的理解需求，
Curator 可以建立 Semantic Relationship——前提是 explanation 字段
提供 KG 不包含的理解层次。
```

## §5 Relationship Ownership — 谁创建关系？

### 5.1 来源约束

```
M85：Curator authored only。

创建流程：
  1. Curator 识别候选关系对
  2. Curator 分类关系性质（Semantic / KG / Navigation）
  3. 仅 Semantic 类型进入 related_causal_objects
  4. Curator 撰写 explanation 文本
  5. Curator 设定 relation_type
```

### 5.2 禁止的来源

| 来源 | 禁止理由 |
| --- | --- |
| AI/LLM 推理 | M83 D6 — AI 不生成 CausalStatement；同理 AI 不生成 Semantic Relationship |
| KG topology 自动推导 | 违反 C1 — KG 连接 ≠ Semantic 连接 |
| Explorer 行为数据 | 行为数据产生 Navigation，不是 Semantic |
| 协同过滤/相似度 | 推荐引擎 → M86+ |

### 5.3 验证来源

```
M85 Validation = Explorer 是否使用 related_causal_objects

如果 Explorer 点击 related_causal_objects 的比例 > 20%：
  → Curator 判断与 Explorer 需求一致

如果 Explorer 忽略 related_causal_objects 但自己建立关系：
  → Curator 判断需要修正（类似 P2 修正案例）
```
