# M85.14 Explorer Experience Specification
### Strict Read-Only / Experience Design Baseline

> 模式声明：严格只读体验设计规格。未修改代码、未创建组件、未输出 React/CSS/API 实现、未进入 M86 开发、未提出代码方案。基于 M85.11.1 / M85.11.2 / M85.11.3 / M85.12 / M85.13 五项输入，将 A 类 Gap 转换为可执行的体验规格。不是 PRD，不是 UI 设计，不是技术方案——是从"Engine Evolution"转向"Explorer Experience Evolution"的设计规格基线。

## Part 1 — Experience North Star

### 用户第一分钟应该理解什么？

**"这是帮我理解历史的，不是让我翻数据库的。"**

用户应该立即感知三件事：
1. 这里不需要先懂很多——一个好奇就够了。
2. 有一条清晰的路可以走——不用自己摸索。
3. 有一个"对话伙伴"在——不是孤单的阅读。

第一分钟结束时，用户的心理状态应该是：**"我知道我想理解什么，而且路已经铺好了。"** 而非："我不知道该点什么。"

### 第五分钟应该获得什么认知变化？

**从"模糊好奇"到"看见真实"。**

用户应该经历了：
- 选定了一个他真正好奇的方向
- 看到了 2-3 个具体的、可想象的历史对象
- 理解了每个对象为什么在这条线上
- 开始注意到它们之间可能存在关系

第五分钟结束时，用户的心理状态应该是：**"原来这件事具体是这样的——我开始有点感觉了。"** 而非："我看到了很多名字，然后呢？"

### 第十五分钟应该完成什么理解闭环？

**从"看见碎片"到"看懂一条逻辑"，并产生一个新问题。**

用户应该经历了：
- 把至少两个碎片连成了一条他认可的因果/影响逻辑
- 收到了"你刚才看懂了这个"的确认
- 脑中自然浮现了一个更深的问题
- 知道可以停在这里，也可以继续

第十五分钟结束时，用户的心理状态应该是：**"原来如此——那它后来又影响了什么？"** 而非："我点了十几个东西，然后不知道该干嘛了。"

## Part 2 — Experience Capability Model

将 M85.13 A 类 7 个 Gap 转化为 7 项体验能力。

### Capability 1 — Curiosity Entry（好奇入口）
- **当前问题**：用户打开产品后面对技术代号矩阵（`m77-package-01`）和内部指标（深度/覆盖），不知道选什么，不知道选了会发生什么。
- **目标体验**：用户能够从自己的好奇出发，被引导进入一条可理解的探索路线——不需要先验知识，不需要理解系统结构。
- **用户心理变化**：从"我不知道该选什么" → "这个正好是我想知道的"。
- **成功标准**：用户在看到入口后的 30 秒内，能用自己的话说出"我要理解的是 X"。犹豫时间不超过一次扫视。
- **失败表现**：用户在看到入口后持续扫视超过 1 分钟仍未选择；或随机选择后问"这是什么意思"（违反 P01、P03）。

### Capability 2 — Orientation（定位锚定）
- **当前问题**：选定方向后直接坠入实体列表，没有任何"你即将经历什么"的定位，用户怀疑自己走错了。
- **目标体验**：用户选定方向后，立即获得一段定位——"你要理解的是 X，接下来会一步步看到 Y，最终你会看懂 Z"。
- **用户心理变化**：从"我是不是走错了" → "好，我知道了，走吧"。
- **成功标准**：用户在看到定位后，不再有"退回重选"的冲动，注意力转向"那第一个是什么"。
- **失败表现**：用户看完定位后仍感到不安，退回入口或随机点击第一个实体（违反 P01、P12）。

### Capability 3 — Navigation Contract（导航契约）
- **当前问题**：每一次跳转都是认知断裂——用户不知道从哪来、为什么看到这个、看了能更懂什么。
- **目标体验**：每一次从 A 到 B 的移动，都携带可感知的 From（来源）/ Why（原因）/ Value（价值）三元信息。用户不是因为"系统有这个"而跳转，而是因为"理解自然引出它"。
- **用户心理变化**：从"我怎么到这了" → "哦，因为刚才那个，自然就想看这个"。
- **成功标准**：用户在跳转后 5 秒内能回答"为什么我现在看这个"。连续 3 次跳转不产生"我怎么到这了"的困惑。
- **失败表现**：用户跳转后问"这和我刚才看的有什么关系"；或连续跳转 3 次以上无认知推进（违反 P01、P05、P08、P09）。

### Capability 4 — Semantic Connection（语义连接）
- **当前问题**：实体间、CausalObject 间的关系仅显示名字或类型标签（如 `causes`），不解释"为什么 A 和 B 相关对理解这条线意味着什么"。
- **目标体验**：每当用户看到两个对象之间的连接，都能获得一句"为什么它们相关，以及这说明了什么更大规律"的语义解释。
- **用户心理变化**：从"哦，它们是相关的" → "原来它们的关联说明了这个"。
- **成功标准**：用户在看到关系后，能用自己的话复述"因为 A 所以 B，这让我理解了 X"。无"所以呢"的悬空感。
- **失败表现**：用户看完关系后，无法解释它们为何相关，或将其视为随机并排（违反 P08）。

### Capability 5 — Understanding Completion（理解闭环）
- **当前问题**：用户积累了大量信息，但产品从未给出"你现在看懂了"的闭合信号。探索无休止点，无成就感。
- **目标体验**：当用户将至少两个碎片连成一条逻辑后，产品主动确认"你看懂了 X"，并结构化呈现用户刚才走通的理解。
- **用户心理变化**：从"我看了好多，然后呢" → "原来如此——我真的看懂了"。
- **成功标准**：用户在看到理解闭环后，产生满足感或主动说出"原来如此"。不会立即继续盲目跳转。
- **失败表现**：用户持续跳转但无"懂了"的感觉；或被迫在伪终点（空 tab）停下（违反 P06）。

### Capability 6 — New Question（新问题孵化）
- **当前问题**：理解后无任何引导，用户要么转圈要么放弃。体验在信息层封口，无法形成可持续的认知螺旋。
- **目标体验**：每一次理解闭环的同时，产品将自然引出的新问题显形并递回给用户——"你刚看懂了 X，这自然让你想问 Y，要继续吗？"
- **用户心理变化**：从"懂了，但然后呢" → "我还想知道那个"。
- **成功标准**：用户在看到新问题后，至少有 50% 的概率选择继续探索而非离开。新问题由用户主动选择是否继续（非推送）。
- **失败表现**：新问题由算法决定（违反 P07）；或理解后直接封口无任何续接提示（违反 P06、P07）。

### Capability 7 — Core Value Discovery（核心价值主动可见）
- **当前问题**：AI 对话伙伴、理解种子、工作台全部默认收起或藏在脚注。用户不知道它们存在，等于核心能力不存在。
- **目标体验**：AI 对话伙伴、理解种子、工作台作为"探索工具"始终主动可见——不是需要挖掘的彩蛋，而是用户探索过程中自然会用到的基础设施。
- **用户心理变化**：从"这产品只有实体列表吗" → "原来我随时可以问、随时可以看懂了什么、随时可以回看走过的路"。
- **成功标准**：用户在第一分钟内发现 AI 对话伙伴的存在；在第三分钟内发现理解种子；在需要回看时不超过一次操作找到工作台。
- **失败表现**：用户完成探索后仍不知道可以问 AI；或从未见过理解种子（违反 P04）。

## Part 3 — Explorer Experience Flow Specification

### Curiosity → Orientation
- **用户进入状态**：有模糊好奇，或刚刚从上一轮理解的 New Question 而来。
- **用户期待**：找到一个能接住我好奇的入口，不需要先懂很多。
- **产品必须提供**：以"人会好奇的问题"为入口（如"一个文明如何兴起又消失？"），而非技术代号或搜索框。
- **用户离开时认知变化**：从"我有个模糊好奇" → "我知道我要理解 X"。
- **禁止出现的失败状态**：用户因入口语言（代号/指标）而退却；用户随机选择；用户无法将入口与自己的好奇关联。

### Orientation → Discovery
- **用户进入状态**：已选定方向，需要确认"我走对了吗"。
- **用户期待**：一句承诺——这条路会帮我理解什么。
- **产品必须提供**：一段定位（"你要理解的是 X，接下来会一步步看到 Y"）+ 第一个关键对象的预览。
- **用户离开时认知变化**：从"我选了这个" → "好，路铺好了，开始看"。
- **禁止出现的失败状态**：直接坠入信息洪流无定位；用户怀疑选错并退回。

### Discovery → Connection
- **用户进入状态**：已看到 2-3 个具体对象，开始注意到它们之间可能有关联。
- **用户期待**：它们为什么在一起？这说明了什么？
- **产品必须提供**：带语义的关系解释（"因为 A 所以 B，这帮你理解 X"），而非仅并排或超链接。
- **用户离开时认知变化**：从"我看到了几个东西" → "它们是这样连起来的"。
- **禁止出现的失败状态**：关系仅显示名字/标签无语义；无限横向跳转同密度数据。

### Connection → Understanding
- **用户进入状态**：已把至少两个碎片连成逻辑，需要确认"我是不是看懂了"。
- **用户期待**：一个确认——"是的，你刚才看懂了这个"。
- **产品必须提供**：理解闭环信号——结构化呈现用户刚走通的逻辑链，并点明"这些在一起说明了什么"。
- **用户离开时认知变化**：从"它们是这样连的" → "原来如此——我懂了"。
- **禁止出现的失败状态**：无闭环信号，用户持续跳转无休止；伪终点（空 tab）中断探索。

### Understanding → New Question
- **用户进入状态**：旧疑问闭合，新疑问自然浮现。
- **用户期待**：我还能知道什么？我不想就这样结束。
- **产品必须提供**：将自然引出的新问题显形，递回为用户自主选择——"你刚看懂了 X，这自然让你想问 Y"。
- **用户离开时认知变化**：从"原来如此" → "那接下来呢？"（同时具备"我可以停，也可以继续"的自由）。
- **禁止出现的失败状态**：算法替用户决定下一步（违反 P07）；理解后直接封口无续接。

## Part 4 — Navigation Contract Specification

### 基础体验协议

History Explorer 中任何两个可探索对象之间的移动，必须遵守 Navigation Contract：

- **From（来源）**："我从哪里来？"——保留来路，用户随时可退。
- **Why（原因）**："为什么此刻看到它？"——不是"系统有这个"，而是"你刚才的理解自然引出它"。
- **Value（价值）**："它帮我理解什么？"——指明这一步在认知地图上的位置。

### 各载体间的移动规则

**Entity → Entity**：From：你正在理解 X 线上的某个对象。Why：这两个对象在 X 线上是因果/影响/同源关系。Value：它们的关联帮你理解 X 是如何推进的。

**Entity → CausalObject**：From：你正在看一个历史对象。Why：这个对象背后有一个改变走向的关键原因。Value：理解这个原因，你就知道"为什么它发生了"。

**CausalObject → CausalObject**：From：你刚理解了一个关键原因。Why：这个原因引发或关联了另一个关键原因。Value：把原因连起来，你就能看懂一条完整的因果链。

**Any → AI Companion**：From：你正在探索 X 线上的某个节点。Why：你可能想就当前看到的内容提问。Value：对话伙伴知道你在哪，能给你上下文相关的解释。

**Any → Workspace**：From：你已经走过了一段探索。Why：你可能想回看、续接、或整理理解。Value：你走过的路，这里都记着——不是堆积的记录，而是你的认知轨迹。

**Any → Timeline / Map / 未来载体**：From：你正在理解 X 线上的某个对象。Why：这个对象在时间/空间/叙事上还有更多维度。Value：换个角度，你能看到同一件事的更多面。

### 协议失败判定

任何一次移动后，如果用户产生以下任一疑问，Navigation Contract 即被判定为未履行：
- "我怎么到这的？"
- "这和刚才有什么关系？"
- "看这个能帮我理解什么？"

## Part 5 — Understanding Model Specification

### Cognitive Completion Model（认知完成模型）

理解不是二元状态（"懂了" vs "没懂"），而是一个沿五层递进的认知结构变化：

**Layer 1：事实确认（Fact）**
- 用户心理状态："这个东西确实存在/发生了。"
- 产品需提供：具体对象的基本信息 + 它为何在这条线上。
- 完成标准：用户能说出"这个对象是什么、它在这条线上的角色"。
- 不可用指标：点击数、页面浏览数。

**Layer 2：解释获取（Explanation）**
- 用户心理状态："我明白它为什么会发生/为什么重要。"
- 产品需提供：可溯源的解释（Causal Statement），回答"为什么"。
- 完成标准：用户能用自己的话复述"这件事为什么发生"。
- 不可用指标：停留时间。

**Layer 3：关系建立（Connection）**
- 用户心理状态："这件事和那件事是连在一起的。"
- 产品需提供：带语义的关系解释（"因为 A 所以 B，这说明了 X"）。
- 完成标准：用户能把至少两个碎片连成一条他认可的因果/影响逻辑。
- 不可用指标：关系查看次数。

**Layer 4：理解形成（Understanding）**
- 用户心理状态："原来如此——这些在一起说明了一件更大的事。"
- 产品需提供：理解闭环确认——结构化呈现刚走通的逻辑链 + "这些在一起意味着什么"的点明。
- 完成标准：用户产生"原来如此"的闭合感，并主动说出/意识到自己看懂了什么。
- 不可用指标：任何行为指标。

**Layer 5：新问题孵化（New Question）**
- 用户心理状态："懂了，但我想知道更多——那个呢？"
- 产品需提供：将理解自然引出的新问题显形，递回为用户自主选择。
- 完成标准：用户脑中的旧疑问被替换为一个更聪明的新疑问。
- 不可用指标：续探率（因续探是用户主动选择，非指标驱动）。

### 理解完成 ≠ 探索结束

理解完成（Layer 4）与探索结束是两个独立事件。理解完成是认知结构变化，探索结束是用户选择暂停。用户可以理解完成后暂停（"我懂了，先停在这"），也可以在理解完成前暂停（"有点累了，先回来"）——后一种情况产品应在回归时帮用户接续。

## Part 6 — M86 Scope Boundary Definition

### 必须进入 M86（Experience Critical）

| # | Experience Capability | 价值影响 | 宪法严重度 | 优先级 |
|---|---|---|---|---|
| A1 | Curiosity Entry | 极高 | P01+P03 Critical | **P0** |
| A2 | Orientation | 极高 | P01+P12 Critical | **P0** |
| A3 | Navigation Contract | 极高 | P01+P05+P08+P09 Critical | **P0** |
| A4 | Semantic Connection | 高 | P08 Critical | **P1** |
| A5 | Understanding Completion | 极高 | P06 Critical | **P0** |
| A6 | New Question | 高 | P07 Critical | **P1** |
| A7 | Core Value Discovery | 极高 | P04 Critical | **P0** |

P0（5 项）：进入 M86 第一优先级，是"体验存在"的最低门槛。P1（2 项）：进入 M86 但可在 P0 就位后并行或紧随。

### 可以进入 M86（Experience Enhancement）

| # | Gap | 价值影响 | 宪法严重度 |
|---|---|---|---|
| B1 | 内部概念全量翻译 | 中高 | P03 High |
| B2 | 方向感 / 面包屑 | 中高 | P09 High |
| B3 | 暂停与回归 | 中 | P10 High |
| B4 | 理解种子提升为核心区块 | 高 | P04+P06 High |
| B5 | 伪终点移除 | 中 | P06 Medium |
| B6 | AI Companion 获知上下文 | 中高 | P04+P02 High |
| B7 | Workspace 转为上下文轨迹 | 中 | P10+P01 High |

B4（理解种子提升）和 B6（AI 获知上下文）应优先于其他 B 类，因为它们直接影响 A5（理解闭环）的完成质量。

### 暂不进入 M86

| # | Gap | 理由 |
|---|---|---|
| C1 | Timeline/Map/Video 载体 | 核心体验未验证前，载体适配是过早优化 |
| C2 | AI Agent | 红线，M86 不引入 |
| C3 | 移动端 | 桌面端验证后再评估 |
| C4 | 搜索框引导 | 补充能力，非核心路径 |

## Part 7 — M86 Entry Gate

### M85.14 完成后的前置判断

以下三项全部满足，才允许进入 M86：
1. **M85.11.1 ~ M85.14 全链路文档已落盘且无矛盾**。✅（M85.14 完成后即满足）
2. **八条核心宪法被确认为 M86 不可妥协基线**。✅（M85.11.3 已确立）
3. **M86 的第一批开发范围明确来自本规格 Part 6 的 P0 项（5 项），而非功能清单**。⬜（待 M85.15 Scope Freeze 确认）

### M86 第一阶段应该验证什么？

不是"功能是否完成"，而是：**一个普通用户是否真的能在 15 分钟内完成一轮完整文明理解。**

验证对象（按优先级）：
1. **Curiosity Entry + Orientation**：用户能否在 30 秒内选定方向并感到"路已铺好"？
2. **Navigation Contract**：用户连续跳转 3 次后，能否回答"为什么现在看这个"？
3. **Understanding Completion**：用户在走完一条逻辑链后，是否产生"原来如此"？
4. **Core Value Discovery**：用户在第一分钟内是否发现了 AI 对话伙伴？在第三分钟内是否发现了理解种子？

验证方式：不是 A/B 测试或埋点——而是真实用户的行为观察 + 出声思维（Think Aloud）。M85.11.1 的研究方法在此复用。

### 哪些体验原则不可被开发妥协？

八条核心宪法在 M86 开发过程中**不可议价**：P01 永远知道为何在此 / P02 认知推进优先于信息增量 / P03 翻译为人的语言 / P04 核心价值主动可见 / P05 跳转有认知目的地 / P06 理解形成闭环信号 / P07 疑问驱动而非推荐驱动 / P08 关系带语义。任何开发决策如果与以上任一冲突，应**否决该决策**，而非修改宪法。

### 哪些能力必须先验证用户理解，而不是功能完成？

1. **Curiosity Entry**：用户是否能将入口与自己的真实好奇关联？（功能完成 = 入口存在；体验存在 = 用户主动选择并感到"这正是我想知道的"）
2. **Orientation**：用户读完定位后是否真正感到安心？（功能完成 = 定位文案存在；体验存在 = 用户不再想退回）
3. **Understanding Completion**：用户是否真的产生"原来如此"？（功能完成 = 闭环 UI 存在；体验存在 = 用户主动表达理解）
4. **Core Value Discovery**：用户是否真的发现了 AI 和种子？（功能完成 = 它们可见；体验存在 = 用户自然使用它们）

---

## 最终定位

M85.14 不是 PRD，不是 UI 设计，不是技术方案。

它是 History Explorer 从 **Engine Evolution** 转向 **Explorer Experience Evolution** 的设计规格基线——用体验语言（而非代码语言、组件语言、页面语言）定义了 M86 应该交付的 7 项体验能力，以及每一阶段用户应该经历的认知变化。

**完成 M85.14，下一步是 M85.15 M86 Scope Freeze——将本规格中的 P0 项冻结为 M86 的不可变更开发范围。之后，才允许进入 M86 Implementation。**

## 附：Founder 评价与路线修正（2026-08-06）

### M85.14 的战略意义

**M85.14 是 M80 之后最重要的里程碑。** 之前所有里程碑回答"能不能造出来"，M85.14 开始回答"人类会不会用"。这是产品从技术项目进入真正产品阶段的分界线。

### 两阶段评价体系转换

- M1-M85：证明"文明理解引擎可以存在"（评价标准：技术完备性）
- M86+：证明"普通人真的可以通过它理解文明"（评价标准：人类认知变化）

### 三大战略判断

1. **Navigation Contract 应升级为 Explorer Engine 的第一性原理。** History Explorer 区别于 Wikipedia 的，不是更多资料，而是"每一步都有认知理由"。公式：`看到 A → 因为 A 导致/影响/解释 B → 所以现在看 B → B 让我理解更大的 X`。

2. **Understanding Completion 比 AI Companion 更重要。** 真正的产品单位不是 Page，不是 Answer，而是 **Understanding Loop**（模糊→事实→关系→理解→新问题）。

3. **产品定位升级**：从 `AI + Knowledge Graph + Historical Data Platform` 变为 `A Cognitive Exploration Engine that helps humans transform curiosity into understanding`。M86 不是"前端改版"，是 **History Explorer 1.0 的诞生阶段**。

### M86 Mission Statement（Founder 修正版）

> **让第一次进入 History Explorer 的用户，不依赖历史知识，在 15 分钟内完成一次从问题到理解再到新问题的探索循环。**

（原"完成一轮文明理解"修正为"完成一次探索循环"——重点不是内容多少，而是体验闭环。）

### M85.15 关键纠正

M85.15 不应冻结"5 个功能"，应冻结"5 个用户能力验证目标"（**Experience Outcome Freeze**，非 Feature Freeze）。否则开发团队容易回到旧模式：加字段/加标签/认为完成。

### M85.16 必要性

M86 必须配合 Experience Acceptance Criteria，防止回退成"做几个页面"。验收对象不是代码，而是用户认知。示例格式：

- **EC-001 Curiosity Entry**：成功 = 30 秒内用户能说"我想探索的是这个问题"；失败 = 用户问"这个包是什么意思？"
- **EC-002 Orientation**：成功 = 5 秒内知道要理解什么、为什么从这里开始、接下来会看到什么；失败 = 用户返回重新选择
- **EC-003 Navigation Contract**：成功 = 随机暂停时用户能回答"为什么现在看到这个"；失败 = 回答"不知道，系统推荐的"
- **EC-004 Understanding Completion**：成功 = 用户能复述"原来 A 导致 B，所以 C 发生"；失败 = 只能说"我看了一些资料"
- **EC-005 Core Value Discovery**：成功 = 首次使用主动发现 AI Companion / Understanding Seed / Workspace；失败 = 使用 20 分钟不知道存在
