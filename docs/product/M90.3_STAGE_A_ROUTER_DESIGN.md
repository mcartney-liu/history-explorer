## 0. Stage A 的唯一命题

当前 URL 表达的是**"打开哪个页面"**，Stage A 之后 URL 表达**"用户正在理解什么"**。

Stage A **不改变任何一个像素**。用户看到的界面在 Stage A 结束时应当与今天基本一致——变的是这些界面**由谁决定渲染**。

这一点必须先说清楚，否则 Stage A 会被误判为"没做事"。Stage A 的产出是**结构**，不是**外观**。外观是 Stage B/D 的事。

## 1. 当前路由的真实形态（代码实测）

路由决策**分散在 3 个互不知情的地方**，且存在明确的优先级覆盖关系：

```
App() 函数体
│
├─ [层 1] hash early-return（3 个分支，在 ExplorationShell 之前 return）
│    ├─ :1058  hash === '#/m89'          → 自建 <div class="app-root"> + <header>  ← 绕过 Shell
│    ├─ :1074  hash === '#/dev/catalog'  → <DevCatalog />                          ← 绕过 Shell
│    └─ :1086  hash.startsWith('#/causal/') → <CausalObjectDetailPage />           ← 绕过 Shell
│
├─ [层 2] usePackageContext（唯一订阅 hashchange 的地方）
│    └─ hash '#/package/:slug' → packageSlug 状态
│
└─ [层 3] NavNode 状态机（useNavigationHistory，不写 URL）
     └─ current: topic | entity | causal_object
        └─ 在 ExplorationShell 内部渲染
```

### 由此产生的六个实测缺陷

| # | 缺陷 | 证据 |
|---|---|---|
| D-1 | **同一能力两条渲染路径** | CausalObject：:1091（hash，无 Shell）与 :1353（NavNode，Shell 内） |
| D-2 | **NavNode 不写 URL** | 用户探索到 entity 后刷新页面 → 回到首页。当前探索状态不可分享、不可恢复 |
| D-3 | **hash 变化不触发重渲染** | 只有 `usePackageContext` 订阅了 `hashchange`。`#/m89`、`#/causal/` 依赖"恰好有别的 state 变化"才生效 |
| D-4 | **`#/entity/:gid` 只写不读** | :1097 写入，无任何读取分支 → 死链，用户点击后白屏/无响应 |
| D-5 | **lazy 在 render 函数体内创建** | :1059 每次 render 重建组件类型 → React 视为新类型，卸载重挂 |
| D-6 | **Landing 与 Discover 同屏并列** | :1374 与 :1380 是顺序渲染不是二选一 |

> D-2 是被低估的一项。它意味着**今天的产品无法分享一次探索**。Stage A 顺带修复它——不是额外工作，是 URL 成为真相源的自然结果。

## 2. 目标架构

### 2.1 单向数据流

```
                    ┌──────────────────┐
   URL (hash)  ────▶│   parseRoute()   │  纯函数，无 React 无 DOM
                    └────────┬─────────┘
                             ▼
                        RouteState
              { topic, mode, focus, invalid? }
                             │
                    ┌────────▼─────────┐
                    │   useRouter()    │  唯一 hashchange 订阅点
                    └────────┬─────────┘
                             ▼
              ┌──────────────────────────────┐
              │ { route, navigate, replace } │
              └──────────────┬───────────────┘
                             ▼
                    ┌────────────────┐
                    │     App        │  只做一件事：把 route 交给 Shell
                    └────────┬───────┘
                             ▼
                    ┌────────────────┐
                    │ ExplorationShell│  Stage A 不改其内部实现
                    └────────────────┘
```

**关键约束**：`parseRoute` 不 import React。它可以在 Node 下直接单元测试——这与项目既有的 `navigation.ts` / `searchNav.ts` 纯函数模式一致，不引入新范式。

### 2.2 Route Schema

```
#/explore/:topic
#/explore/:topic/:mode
#/explore/:topic/:mode/:focus
```

保留两个非探索路由（它们不表达"理解"，不应套 explore 语义）：

```
#/            → Home（Discover/Landing 入口）
#/dev/catalog → 开发工具，保留但明确标注非产品路由
```

### 2.3 Mode Registry（Stage A 只定义，不实现渲染）

| Mode | slug | 认知层 | Stage A 状态 |
|---|---|---|---|
| Exploration | `exploration` | Fact | 注册（默认 Mode） |
| Explanation | `explanation` | Explanation | 注册 |
| Relationship | `relationship` | Understanding | 注册 |
| Understanding | `understanding` | Experience Runtime | 注册 |
| Civilization | — | M86+ | **不注册** |
| Map | — | 不存在 | **不注册**（J-1） |

Registry 是**一个数组常量 + 一个校验函数**，不是框架。未注册的 mode 出现在 URL 中时按"无效 mode"处理（见 §5.2）。

> Map 与 Civilization 的扩展位体现在"Registry 是可扩展的数据结构"这一事实上，**不写占位条目**。写占位条目会让 Stage D 的 Panel 计数与 Mode 覆盖率验收产生假阳性——这正是 J-1 批准 Reserved 的原意。

## 3. Route Migration Table

### 3.1 URL 映射

| # | 旧 URL | 新 URL | 转换时机 | 说明 |
|---|---|---|---|---|
| R-1 | `#/m89` | `#/explore/french-revolution/understanding` | 启动一次性重写 | topic 硬编码为 `french-revolution`——这是**如实反映现状**，M89 当前确实只有该主题数据。Stage C 泛化后此映射自然失效并删除 |
| R-2 | `#/causal/:id` | `#/explore/:topic/explanation/:id` | 启动一次性重写 | topic 由 `causal_objects.json` 反查（见 §3.3） |
| R-3 | `#/package/:slug` | `#/explore/:slug/exploration` | 启动一次性重写 | package slug 直接作 topic slug |
| R-4 | `#/entity/:gid` | `#/explore/:topic/exploration/:gid` | **不做兼容** | D-4 死链，从未成功渲染过。为不存在的能力写迁移代码是给"看起来完整"付费 |
| R-5 | `#/dev/catalog` | 不变 | — | 非产品路由 |
| R-6 | `#/`、空 hash | 不变 | — | Home |

### 3.2 内部导航映射（NavNode → Route）

这是 D-2 的修复。NavNode 状态机保留（Stage A 不重构它），但**每次 navigate 同步写 URL**。

| NavNode | 写入 URL |
|---|---|
| `{type:'topic', topic}` | `#/explore/{topic}/exploration` |
| `{type:'entity', id}` | `#/explore/{currentTopic}/exploration/{id}` |
| `{type:'causal_object', objectId}` | `#/explore/{currentTopic}/explanation/{objectId}` |

**entity 的 topic 从何而来**：取当前 route 的 topic。若无（从首页搜索直接跳 entity），使用 `resolveEntityTopic(gid)`——从 `explorationPackages` 反查该 entity 归属的第一个 package slug；仍无则用保留值 `_`（合法 slug 字符，表示"无主题上下文的 entity"）。

> 我选择 `_` 而不是省略 topic 段。省略会让 URL 出现两种形状（`#/explore//exploration/gid`），解析分支立刻增多。单一形状优先。

### 3.3 CausalObject → topic 反查

`causal_objects.json` 已在 App.tsx:111 导入。构建 `objectId → topic` 映射的依据按优先级：

1. 对象自带的 topic/package 归属字段（若存在）
2. 其 `entity_references` 命中的 package slug
3. 兜底 `_`

**实现前必须先验证第 1 项是否存在**。若不存在则只走 2/3。这一点在编码第一步核对，不在设计阶段猜测。

### 3.4 一次性迁移的执行语义（J-3 约束）

```
应用启动（模块加载时，React 渲染之前）
  ↓
读取 window.location.hash
  ↓
命中旧格式？──否──▶ 正常解析
  │是
  ↓
转换为新 URL
  ↓
history.replaceState  ← 不是 location.hash =
  ↓
继续正常解析
```

三个要点：

1. **`replaceState` 而非 `location.hash =`**：后者会产生一条历史记录，用户按返回键会退回旧 URL 再被重写，形成循环。
2. **只在启动执行一次**，不监听、不常驻。
3. **转换后代码中不存在任何生成旧 URL 的路径**——这由 §6 的静态检查保证，不靠自觉。

## 5. Stage A 验收标准

### 5.1 Founder 指定的 4 项

| # | 标准 | 检验方式 |
|---|---|---|
| A-1 | 所有 route 经统一 Router | `grep -c "window.location.hash"` → **1**（仅 useRouter.ts） |
| A-2 | Router 输出 params + Mode，非 Component | `parseRoute` 返回类型中不含 `ReactNode`/`ComponentType`；无 JSX import |
| A-3 | 所有入口进入 ExplorerShell | App.tsx 中 `return` 语句数 = 1 |
| A-4 | App.tsx ≤ 200 行 | 见 §5.3 |

### 5.2 新增：Route Identity Test（Founder 指定）

自动化测试，5 个入口断言同一结构：

```
入口                      → 断言
─────────────────────────────────────────────
首页 → 点击主题            → Shell 存在 · Session 存在 · mode=exploration
探索包 (#/package/x)       → Shell 存在 · Session 存在 · mode=exploration
Entity (点击实体)          → Shell 存在 · Session 存在 · mode=exploration · focus≠null
CausalObject (#/causal/x)  → Shell 存在 · Session 存在 · mode=explanation
M89 (#/m89)                → Shell 存在 · Session 存在 · mode=understanding
```

每个入口额外三条否定断言：

- 渲染树中 `<header>` 出现次数 == Shell 自身的数量（不因入口不同而增加）
- 不存在 `.app-root` 以外的顶层布局容器
- Shell 组件实例数 == 1

**任一入口渲染出独立 Header / Layout / Page → Stage A 不通过。**

> 诚实说明：M89 入口能通过此测试的前提是把 `<M89Workspace />` 放进 Shell 的 children。它内部仍会带自己的样式和 frenchRevolution 耦合——**这是 Stage C 的债，Stage A 不还**。Route Identity Test 检验的是"容器是否统一"，不是"内容是否泛化"。这个边界如果不写明，Stage A 会被无限拖长。

### 5.3 关于 App.tsx ≤ 200 行——必须现在说清楚

**Stage A 单独无法达成 200 行。**

现状 1424 行的构成（实测）：

| 部分 | 行数 | 归属 Stage |
|---|---|---|
| import | ~115 | D（组件消失后自然减少） |
| 路由 hash 分支 | ~50 | **A** |
| 数据获取 / fetchNode / useEffect | ~400 | B/C |
| 业务 handler（openEntity/openPackage/handleSearch…） | ~300 | B/C |
| ExplorerRuntimeContext 装配 + Projection + Memory | ~200 | E |
| topic/entity 分支内联 JSX（20+ Panel） | ~300 | **D** |
| 其他 | ~60 | — |

Stage A 能移除的是**路由 ~50 行**，加上 import 减少，实际落点约 **1350 行**。

**我不会为了让数字好看，在 Stage A 把 400 行数据逻辑搬进新文件。** 那是"把行数移到别处"，不是收敛，而且会污染 Stage B/C 的验收基线——搬过一次的代码，Stage B 再搬第二次，两次都无法验证正确性。

**建议**：`App.tsx ≤ 200 行` 保留为 **M90.3 全程终点指标**，Stage A 的门槛改为：

- App.tsx 中 `return` 语句数 = **1**（结构性判据，不可用移动代码作弊）
- App.tsx 中 `window.location.hash` 出现次数 = **0**
- 行数记录为过程指标，不作为 Stage A 通过条件

这需要 Founder 裁决。若坚持 Stage A 即达 200 行，则 Stage A 实际等于 Stage A+B+C 合并执行，"Stage A 只做 Router"的约束自相矛盾。

## 6. 防回归机制

一次性迁移之后如何保证不再产生旧 URL——不能靠约定：

1. **静态检查**：`scripts/` 下新增校验，`window.location.hash` 赋值只允许出现在 `routing/useRouter.ts`。其余文件命中即失败。
2. **类型约束**：`buildHash()` 只接受 `RouteState`，无法构造 `#/m89` 形状的字符串。
3. **`legacyRedirect.ts` 自带失效期注释**：明确标注 Stage C 完成后 R-1 删除、全部旧格式在 M91 删除。

第 1 项是唯一真正有效的——2 和 3 都可被绕过。

## 7. 风险说明

### R-A（高）— App.tsx 是活跃开发文件

**风险**：1424 行、28 个未推送提交、当前有未暂存修改。改动路由会与进行中的工作冲突。

**缓解**：Stage A 对 App.tsx 的改动集中在 :1057-1108 与末尾 return，**不触碰中间 900 行业务逻辑**。改动前确认工作区干净或已提交。

### R-B（高）— hash 与 NavNode 双状态源短期并存

**风险**：Stage A 后 URL 成为真相源，但 NavNode 状态机仍然存在（Stage A 不重构它）。两者需保持同步，存在不一致窗口——典型场景：浏览器返回键改变 hash，NavNode cursor 未同步。

**缓解**：确立**单向规则** —— NavNode 变化 → 写 URL；URL 变化（外部/返回键）→ 重建 NavNode。禁止双向监听。同步点收敛在 App 的一个 `useEffect` 内。

**残留风险承认**：这是 Stage A 引入的临时复杂度，Stage B/C 移除 NavNode 后消失。若 Stage B 长期不做，这个双状态会成为新的债。**Stage A 与 Stage B 之间不应有长间隔。**

### R-C（中）— CausalObject topic 反查可能失败

**风险**：§3.3 的三级兜底若全部落到 `_`，`#/causal/co-004` 会转换成 `#/explore/_/explanation/co-004`，URL 语义退化。

**缓解**：编码第一步验证 `causal_objects.json` 结构。若归属信息缺失比例高，改为在 `routeSchema.ts` 维护显式映射表（数据量小，可接受）。

### R-D（中）— M89 进 Shell 可能视觉破损

**风险**：`UnderstandingWorkspace` 当前假设自己占满全屏、自带 header。放进 Shell children 后可能出现双 header、宽度溢出、样式冲突。

**缓解**：Stage A 只保证**结构正确**（在 Shell 内、Route Identity Test 通过）。视觉破损**允许存在**并记录为 Stage B 待修项。

**这一点需要 Founder 确认接受**：Stage A 结束时 M89 页面可能比现在难看。若不接受，Stage A 需要包含少量视觉修补，但那违反"Stage A 只做 Router"。我建议接受破损——**让债务可见，好过让它藏在一个绕过 Shell 的分支里**。

### R-E（低）— 用户已收藏的旧 URL

**风险**：外部链接指向 `#/m89` 等。

**缓解**：一次性迁移覆盖 R-1/R-2/R-3。`#/entity/:gid`（R-4）不覆盖——它从未工作过，不存在有效收藏。

### R-F（低）— 测试基础设施

**风险**：Route Identity Test 需要渲染完整 App（含数据获取）。若现有 vitest 配置无 fetch mock，测试会因网络失败而非路由问题失败。

**缓解**：编码前确认 `frontend/` 测试配置现状。若缺失则先补最小 fetch mock——这属于 Stage A 必要成本，不是范围蔓延。
