## 0. 核心原则

```
History Explorer 不是在建设 Engine，而是在建设 Explorer Habit。

Explorer Habit = 用户形成 "理解 → 关联 → 继续探索" 的认知模式。

这个 Contract 保护的不是代码，而是这个认知模式不被破坏。
```

---

## Contract 1 — 入口必须从问题开始

### 规则

```
任何 CausalObject 的一级入口，必须以 "文明问题" 而非 "历史对象" 呈现。

✅ 允许：
  "为什么中国形成中央官僚体系？"
  "不同文明如何解决治理问题？"
  "技术如何改变知识传播？"

❌ 禁止：
  "秦朝"
  "罗马法"
  "制度演化"
  "热门历史"
  "推荐内容"
```

### 代码约束

```typescript
// UnderstandingSeed 类型约束
interface UnderstandingSeed {
  question: string          // required — 用户可见的问题
  relationLabel: string     // required — 内部标签（小号副标题）
  entryObjectId: string     // required — 入口 CausalObject ID
  path: string              // required — 路径预览（如 "秦制 → 科举 → 文官体系"）
}
```

### 测试保护

```
1. DiscoverPage 中 UnderstandingSeeds 组件：
   - 每个 Seed 卡片必须有 question 文本（非空）
   - 每个 Seed 卡片必须有 entryObjectId（有效 ID）
   - Seed 卡片不包含 "推荐"/"热门"/"相关" 等推荐引擎词汇
```

## Contract 2 — 关系必须有解释

### 规则

```
任何 Semantic Relationship 在 UI 中展示时，
必须同时展示 relation_type 标签 + explanation 全文。

✅ 允许：
  [制度演化] 科举 → 文官体系
  秦代建立的中央集权框架，使科举成为标准化选官的必然选择。
  → 探索 科举 → 文官体系

❌ 禁止：
  科举 → 文官体系  （裸连接，无 explanation）
  [制度演化] 科举制度  （无 explanation 文本）
```

### 代码约束

```typescript
// RelatedCausalObjectRef 在 UI 中的约束
// CausalObjectDetailPage 的 related_causal_objects 渲染必须包含：
// 1. relation_type 标签（彩色标签）
// 2. target 名称（人类可读）
// 3. explanation 全文
// 4. CTA（"探索 %{name}"，非 "了解更多"/"推荐阅读"）
```

### 测试保护

```
1. CausalObjectDetailPage 中 related_causal_objects 渲染：
   - 每个 ref 必须渲染 explanation 文本
   - 每个 ref 必须渲染 relation_type 标签
   - CTA 文案为 "探索 %{name}"，不含 "推荐"/"了解"/"查看"
   - explanation 为空时，ref 不渲染（或标记为错误）
```

## Contract 3 — 导航由理解驱动，非推荐驱动

### 规则

```
Explorer 的下一步必须由 curator 的 understanding 关系驱动，
不由推荐算法、点击率、热度排序驱动。

✅ 允许：
  CausalObjectDetailPage Act 2：related_causal_objects（curator 策展）
  CausalObjectDetailPage Act 3：related_entities + exploration_paths（KG 关系）

❌ 禁止：
  "你可能还想了解"（推荐引擎语言）
  "热门历史"（点击率排序）
  "猜你喜欢"（协同过滤）
  "相关推荐"（推荐算法）
```

### 代码约束

```
App.tsx 中：
  - 不引入任何推荐算法 / 排序逻辑
  - 不基于用户行为数据决定下一个 CausalObject
  - onCausalObjectClick 只响应 curator 策展的 related_causal_objects

CausalObjectDetailPage 中：
  - 不引入任何 "recommended" / "popular" / "suggested" 区块
  - Act 3 "继续探索" 只展示 related_entities + exploration_paths
```

### 测试保护

```
1. App.tsx 中无 recommendation/recommend 函数或 import
2. CausalObjectDetailPage 中无 "推荐"/"热门"/"猜你喜欢" 文本
3. Understanding Journey 流转不基于任何用户行为排序
```

## Contract 4 — 用户语言，非架构语言

### 规则

```
UI 中使用的文本必须是用户认知模型中的概念，
不得暴露架构模型中的术语。

✅ 允许：
  "为什么会发生？"（非 "Explanation Layer"）
  "产生了什么影响？"（非 "Consequence"）
  "理解关联"（非 "Semantic Relationship Layer"）
  "继续探索"（非 "Exploration Paths"）

❌ 禁止：
  "Fact Layer"
  "Explanation Layer"
  "Understanding Layer"
  "Semantic Relationship"
  "Causal Object"
  "relation_type: institutional_evolution"（作为主文案）
```

### 代码约束

```
所有 i18n 键中：
  - 面向用户的键使用用户语言（causal.mechanism = "为什么发生"）
  - relation_type 标签仅作为副标签（小号金色标签），不作为主标题
  - UnderstandingSeeds 的 question 字段是用户语言
```

## Contract 5 — Seed ≠ CausalObject

### 规则

```
Understanding Seed 是理解旅程的起点，
不是 CausalObject 的别名。

当前实现：
  Seed → 单一 CausalObject（co-004/co-009/co-008）

未来可能：
  Seed → 多个可能入口 → 不同理解路径

这个约束防止未来把 "Seed 列表" 变成 "CausalObject 列表"。
```

### 代码约束

```typescript
// UnderstandingSeeds 组件签名
// entryObjectId 是当前实现的简化，
// 但组件本身不应假设 "一个 Seed = 一个 CausalObject"
interface UnderstandingSeed {
  question: string          // 用户问题
  entryObjectId: string     // 当前入口 CausalObject（未来可扩展为多个）
  relationLabel: string     // 内部分类标签
  path: string              // 路径预览
}
```
