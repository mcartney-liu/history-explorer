## Check 1 — Event Semantic Accuracy

### 1.1 cs_card_expand — 语义审查

**当前实现**：

```typescript
// CausalStatementCard.tsx L60-63
<div className="causal-card" onClick={handleCardClick}>
  // ... entire card content
</div>

// L42-47
const handleCardClick = useCallback(() => {
  if (cs.id) {
    recordEvent({ action: 'cs_card_expand', causalId: cs.id })
  }
  onCardClick?.()
}, [cs.id, onCardClick])
```

**审查结论**：

| 审查项 | 结果 | 说明 |
| --- | --- | --- |
| 是否只代表 collapse → expand 状态转换？ | ❌ **否** | CausalStatementCard 无 collapse/expand 状态机。每次点击都 emit |
| 是否会产生噪音（空白区域/重复点击）？ | ⚠️ **是** | 点击 Card 任意位置（包括 padding、已阅读文本、evidence refs 边缘）都触发 |
| 事件名是否产生错误语义？ | ⚠️ **是** | 名称暗示 "展开"，但实际上是 "交互" |

**判定**：`cs_card_expand` 的语义不准确。但**不阻塞 Acceptance** — 理由如下：

1. CausalStatementCard 当前没有 collapse/expand 状态 — 不存在 "展开" 这一用户行为，因此 "展开事件" 这个概念在当前 UI 中不存在
2. 将 `cs_card_expand` 理解为 "用户主动交互" 仍然有效 — 它测量的是 "用户是否主动与 CS Card 发生了任何交互"
3. 对 M83.4 验证的影响：**Expand Rate = 交互率**。与 View Rate 的比值仍然是有效的 "参与度" 指标

**建议（记录为 Limitation，不在 M83 修复）**：

| Limitation | 影响 | 建议修复时机 |
| --- | --- | --- |
| L1 — `cs_card_expand` 语义过载：每次点击都触发，而非真实展开行为 | M83.4 的 Expand Rate 实际上测量的是 "任意交互率"，不是 "阅读展开率" | M84 — 当 CausalStatementCard 引入 collapse/expand 状态时，将事件绑定到状态转换而非全局 onClick |

### 1.2 cs_card_view — 语义审查

**当前实现**：

```typescript
// CausalStatementCard.tsx L36-40
useEffect(() => {
  if (cs.id) {
    recordEvent({ action: 'cs_card_view', causalId: cs.id })
  }
}, [cs.id])
```

**审查结论**：

| 审查项 | 结果 | 说明 |
| --- | --- | --- |
| 是否只在可见时触发？ | ❌ **否** | `useEffect` on mount — 即使组件 `display:none` 或 `visibility:hidden`，只要 React mount 就触发 |
| 是否会产生虚假曝光？ | ⚠️ **是** | Tab 切换、Package 预加载等场景可能 mount 但不展示 |
| 对 M83.4 的影响 | 🟡 小 | CausalStatementCard 当前只在 Package Journey 中渲染（无 Tab/预加载场景），虚假曝光概率低 |

**判定**：`cs_card_view` 语义为 "React mount"，非 "用户可见曝光"。但**不阻塞 Acceptance** — 理由：

1. 当前 CausalStatementCard 的渲染场景单一（仅在 Package Journey 中可见渲染），没有 display:none 或预加载场景
2. 引入 IntersectionObserver 会增加实现复杂度（需要 ref + observer + cleanup），违反 M83.1 的轻量化原则

**建议（记录为 Limitation）**：

| Limitation | 影响 | 建议修复时机 |
| --- | --- | --- |
| L2 — `cs_card_view` 基于 mount 而非可见性：display:none 场景会产生虚假曝光 | M83.4 的 View Rate 可能略高于实际曝光率（当前影响小） | M84 — 当 CausalStatementCard 在更多场景中使用时（如 Runtime Explorer / Tab 切换），引入 IntersectionObserver |

### 1.3 cs_follow_entity — 因果关联审查

**当前实现**：

```typescript
// RelationshipChain.tsx L71-75, 84-89
const edge = spine.edges[i]
const edgeCS = edge && causalStatements
  ? resolveCausalForEdge(edge, causalStatements)  // cause_id/effect_id 精确匹配
  : null

onClick: () => {
  if (edgeCS?.id) {  // 仅当当前边有 CS 时触发
    recordEvent({ action: 'cs_follow_entity', causalId: edgeCS.id })
  }
  onEntityClick(gid)
}
```

**`resolveCausalForEdge` 实现**：

```typescript
// explorationGuide.ts L109-119
export function resolveCausalForEdge(
  edge: RelationshipPathRef,
  causalStatements: readonly CausalStatementData[],
): CausalStatementData | null {
  for (const cs of causalStatements) {
    if (cs.cause_id === edge.from && cs.effect_id === edge.to) {
      return cs  // 精确匹配：边的 from/to 必须等于 CS 的 cause_id/effect_id
    }
  }
  return null
}
```

**审查结论**：

| 审查项 | 结果 | 说明 |
| --- | --- | --- |
| causalId 是否绑定到**当前边的 CS**？ | ✅ **是** | `edgeCS` 通过 `resolveCausalForEdge(edge, causalStatements)` 精确绑定到当前边 |
| 是否会出现 "附近有 CS 就绑定" 的污染？ | ✅ **否** | 每段 spine 的 `edge` 是独立的，`edgeCS` 严格基于 `edge.from === cs.cause_id && edge.to === cs.effect_id` |
| 是否正确：Entity A —[CS001]→ Entity B，点击 B → causalId="CS001"？ | ✅ **是** | 点击 B 时，B 对应的 `edge = spine.edges[i]`，该 edge 的 `edgeCS` 已正确解析为 CS001 |
| 是否错误：Entity B 附近有 CS001，但 B 不在 CS001 的边上？ | ✅ **不会发生** | 因为 `edgeCS` 是 `edge` 级别的变量，不是 `gid` 级别的全局查找 |

**判定**：`cs_follow_entity` 的因果关联**完全正确**。causalId 严格绑定到当前边的 CausalStatement，不存在 "附近 CS 污染" 的问题。
