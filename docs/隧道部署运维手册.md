# History Explorer 隧道部署运维手册

> 适用范围：本机（翔哥开发机）上「改代码 → 让公网隧道上的朋友看到效果」的完整流程。
> 读者：任何接手本机开发/发布的人（含 AI 助手）。
> 核心一句话：**改了代码 ≠ 生效**。后端要重启、前端要重建，三者（数据 / 后端 / 前端）版本一致，隧道上才看得到新效果。

## 〇、本地开发环境启动（8001/5174）—— 日常自测用

不用隧道、纯本机自测时走这条链路。它由仓库根目录的一键脚本 `start-dev.sh` 拉起：

- **API 对接**：前端 `VITE_API_BASE=http://localhost:8001`（脚本内已固化），所以 5174 与 8001 自动配对


## 一、架构速览：两条链路（本地 + 隧道）

### A. 本地自测链路（日常开发，推荐自测用）

```
浏览器
   │  http://localhost:5174/
   ▼
Vite dev server（端口 5174，VITE_API_BASE=http://localhost:8001）
   ▼
uvicorn 后端（端口 8001，由 start-dev.sh 起）
   └── 数据：backend/data/examples（10 topics / 184 entities / 357 relationships）
```

### B. 公网隧道链路（给朋友/外网看）

朋友通过公网 URL 访问，请求链路是：

```
朋友浏览器
   │  https://xxx.trycloudflare.com
   ▼
cloudflared 隧道（内网穿透）
   │  转发到 127.0.0.1:4173
   ▼
serve.js 合并服务（端口 4173）
   ├── 静态文件：托管 frontend/dist（前端构建产物）
   └── 反代：/api/、/explore/、/entity/、/topics 等前缀 → 127.0.0.1:8002
        ▼
uvicorn 后端（端口 8002，Python FastAPI）
   └── 数据：backend/data/feedback.jsonl 等（gitignored 运行时数据）
```

| 进程 | 端口 | 角色 | 改什么需要动它 |
|---|---|---|---|
| uvicorn 后端 | 8002 | 提供所有 API | 改了 backend/ 下代码 → **必须重启** |
| serve.js | 4173 | 托管前端 + 反代 API | 改前端只重建 dist 即可，**一般不用重启** |
| cloudflared | 无 | 公网隧道 | 重启后**公网 URL 会变**（临时域名） |

> 注意：**8001/5174 = 本地自测链路**（由 `start-dev.sh` 一键起）；**8002/4173/cloudflared = 公网隧道链路**。
> 两者跑同一份 backend 代码，但互不相通——隧道不走 8001，本地自测不走 8002，别混淆。

## 二、标准发布流程（分三种改动）

### 场景 A：改了后端代码（backend/ 下任意 .py）

```bash
# 1. 改前报备 + 红线自检（团队纪律：动 backend 先跑 freeze-check）
cd /c/Users/haizhi/WorkBuddy/2026-07-13-10-54-28
node scripts/freeze-check.mjs          # 期望输出 M3.5 Freeze Guard PASSED

# 2. 改完代码后，先做「导入自检」——不启动服务就能发现语法/定义错误
cd backend
.venv/Scripts/python.exe -c "from app import main; print('IMPORT_OK')"
# 若报错，说明代码有 bug，先修，不要急着启动

# 3. 重启 8002（关键步骤！旧进程不会自动加载新代码）
#    先看 8002 被哪个 PID 占用
netstat -ano | findstr ":8002" | findstr "LISTENING"
#    杀掉旧进程（把 <PID> 换成上面查到的）
#    用 PowerShell 工具执行：
#    Stop-Process -Id <PID> -Force
#    然后重新启动（后台运行）：
cd backend
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  .venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8002

# 4. 验证后端真的加载了新代码
curl -s http://127.0.0.1:8002/api/v1/feedback/board | head -c 300
```

**最容易踩的坑**：改完代码不重启 → 旧进程继续服务旧逻辑，前端表现一切照旧，
让人误以为"改坏了"或"没生效"。**改 backend = 必须重启 8002**。

### 场景 B：改了前端代码（frontend/src/ 下任意文件）

```bash
# 1. 用一键脚本重建 dist（已锁定 VITE_API_BASE=/ 相对路径，防 localhost 编进线上包）
cd /c/Users/haizhi/WorkBuddy/2026-07-13-10-54-28/frontend
bash build_tunnel.sh

# 2. 验证新构建已生成（看有没有新的 index-*.js）
ls -t dist/assets/index-*.js | head -2

# 3. 刷新隧道页面（浏览器 Ctrl+Shift+R 强制刷新，防缓存旧包）
#    serve.js 托管的是 frontend/dist，重建后自动生效，无需重启 serve
```

**最容易踩的坑**：
- 改完源码但忘了 `build_tunnel.sh` → 隧道托管的是旧 dist，页面毫无变化。
- 手动 `vite build` 而不是用脚本 → 可能把 frontend/.env 里的
  `VITE_API_BASE=http://localhost:8001` 编进线上包，公网下浏览器把 API 请求
  打向**访客自己电脑的 8001 端口**（无服务）→ 页面能开、一切后端交互全挂。
- 为什么必须是 `/`：不能用 `./`（子路径页面会变 `/discover/api/...`）、
  不能留空 `''`（会 fallback localhost:8000）。

### 场景 C：只改运行时数据（如 backend/data/feedback.jsonl）

```bash
# 纯数据改动（回复、补数据）不需要重启任何进程
# 直接用脚本/编辑器改 jsonl，改完立即生效
# 注意：feedback.jsonl 是 gitignored 的运行时数据，不进 git，无需 commit
```

## 三、改完必须验证（发布清单）

每次发布后，按这个顺序过一遍，全绿才算完成：

- [ ] 后端进程在跑：`curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8002/api/v1/feedback/board` → 200
- [ ] 隧道 4173 在跑：`curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:4173/` → 200
- [ ] 隧道页面引用的是新构建：`curl -s http://127.0.0.1:4173/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'` 与 dist 最新文件一致
- [ ] 公网 URL 可访问：`curl -s -o /dev/null -w "%{http_code}" https://<当前域名>` → 200
- [ ] 数据正确：接口返回的内容符合预期（如回复线程条数、时间戳、链接可点）
- [ ] 前端改动：freeze-check PASSED（`node scripts/freeze-check.mjs`）
- [ ] 代码改动：commit + push 共享分支（见下）

## 五、踩坑记录（全部实战发生过的）

### 坑 1：改了后端代码，旧进程还在跑（本次最大教训）
- 现象：明明改了 `feedback.py`，前端看到的还是旧行为。
- 根因：8002 是改代码**之前**启动的旧实例，进程内存里是旧代码，**不会自动热加载**。
- 解法：按场景 A 杀掉旧进程、重启。改 backend 必重启。

### 坑 2：Python 类定义顺序导致启动即崩（NameError）
- 现象：重启后端时进程秒退，`uvicorn` 报
  `NameError: name 'ReplyItem' is not defined`。
- 根因：`feedback.py` 里 `ReplyItem` 类定义在引用它的 `FeedbackEntry` 类**之后**——
  Python 按顺序执行，类被引用时还没定义。
- 解法：把被引用的模型类定义移到引用者之前。
- 教训：**重启失败一定要看完整 stderr**，不要只看"起不来"就换思路。

### 坑 3：前端源码改了，dist 没重建
- 现象：前端组件改了，隧道页面毫无变化。
- 根因：serve.js 托管的是构建产物 `frontend/dist`，源码改动不 build 不生效。
- 解法：`bash build_tunnel.sh` 重建，浏览器强制刷新。

### 坑 4：API 地址被编成 localhost（公网全挂）
- 现象：页面能开，但「大家的声音」等一切后端交互报"无法加载"。
- 根因：`vite build` 时没覆盖 `VITE_API_BASE`，把 `localhost:8001` 编进了线上包；
  公网访客浏览器把 API 请求打向**访客自己电脑**。
- 解法：一律用 `build_tunnel.sh`（锁定 `VITE_API_BASE=/`），别手动 build。

### 坑 5：vite build 被本机安全垫片卡死
- 现象：`vite build` 报 `[safe-delete] 操作失败 ... ETIMEDOUT` 或
  `Error during a 'trash' operation`，但包其实已下载/构建完成。
- 根因：本机 sandbox 的 safe-delete 垫片在清空 outDir 时超时。
- 解法：build 时加 `--emptyOutDir false`（build_tunnel.sh 已内置该参数，见脚本第 27 行），
  或 Bash 工具加 `dangerouslyDisableSandbox: true`。

### 坑 6：环境变量里残留代理，命令连不上网
- 现象：npm / 后端 curl 报 `ECONNREFUSED 127.0.0.1:10808`。
- 根因：shell 里 `HTTP_PROXY/HTTPS_PROXY` 常驻指向本地代理软件，代理关了变量还在。
- 解法：命令前加 `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy`。

### 坑 7：git push 报证书错误
- 现象：`CRYPT_E_REVOCATION_OFFLINE`（公司代理 MITM 导致证书吊销检查不可达）。
- 解法：`git -c http.sslBackend=openssl -c http.sslVerify=false push ...`
  （仅本次命令生效，不写持久配置）。

### 坑 8：电脑重启后进程全掉
- 现象：8002 / 4173 / cloudflared 不在 → 公网 URL 打不开；或 8001/5174 不在 → 本地 5174 打不开。
- 拉起顺序：
  - **若只需本地自测**：直接 `bash start-dev.sh`（一把起 8001 + 5174），无需隧道三件套。
  - **若还要公网隧道**（按序执行）：
    1. 后端 8002：`cd backend && env -u HTTP_PROXY -u HTTPS_PROXY ./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8002`
    2. 合并服务 4173：`cd C:/Users/haizhi/tunnel-he && "C:/Users/haizhi/.workbuddy/binaries/node/versions/22.22.2/node.exe" serve.js 4173`
    3. 隧道：`cd C:/Users/haizhi/tunnel-he && env -u HTTP_PROXY -u HTTPS_PROXY ./cloudflared.exe tunnel --url http://localhost:4173 --no-autoupdate`
- 注意：**免费隧道 URL 是临时的**，重启后从 cloudflared 输出里重新取新域名，
  并同步更新 tunnel-he/README.md 里的 URL 行。

### 坑 9：serve.js 反代前缀不全导致部分接口挂
- 现象：`/api/` 正常，但 `/topics`、`/explore/`、`/entity/` 返回 HTML 而非 JSON。
- 根因：反代只配了 `/api/`，其余前缀没转发。
- 解法：用 `C:/Users/haizhi/tunnel-he/serve.js` 原版（`PROXY_PREFIXES` 已覆盖
  `/api/ /explore/ /entity/ /provenance/ /related-entities /topics /search /health /healthz /ai/`）。
  启动前若 4173 被旧 serve 占用会报 `EADDRINUSE`，先杀旧进程再起。

### 坑 10：手动重启 8001 丢了 CORS 白名单 → 5174 点实体报"无法连接服务器"
- 现象：5174 前端能正常打开，但**点实体 / 四维研究报"无法连接服务器"**；
  可 `curl` 8001 所有路由全 200 —— 后端其实没挂，是浏览器被跨域拦了。
- 根因：手动 `python -m uvicorn ... --port 8001` 重启时**没带 `CORS_ORIGINS` 环境变量**，
  `backend/app/config.py` 默认白名单只有 `http://localhost:5173`，而前端在 5174，
  浏览器跨域请求被拒。
- 解法：**本地后端重启必须走 `bash start-dev.sh`**（脚本内已固化
  `CORS_ORIGINS="http://localhost:5174,http://127.0.0.1:5174"`）。
  验证响应头出现 `access-control-allow-origin: http://localhost:5174` 即修复。
- 教训：
  1. 本地 8001 **别手动 `python -m uvicorn` 起**，否则必丢 CORS 白名单。
  2. 看到「无法连接服务器」先 `curl 127.0.0.1:8001/health` 确认后端活着的——
     跨域报错 ≠ 后端挂，多半是 CORS 白名单问题。
